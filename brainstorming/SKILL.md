# Brainstorming Ideas Into Designs

帮助用户将模糊想法探索为完整设计方案与 spec。

先理解当前项目上下文，再逐个提问细化需求。理解清楚后，呈现设计方案并获得用户确认。

<HARD-GATE>
在呈现设计方案并获得用户确认之前，不得调用任何实现 skill、编写脚手架代码或执行实现动作。无论需求看起来多简单，都必须先完成设计确认。
</HARD-GATE>

## When to use（按需触发）

- 用户的需求描述模糊，目标、约束或成功标准不清晰
- 存在多种可能的设计方向，需要对比权衡
- 需要在动手前先收束设计，避免返工
- 用户主动要求"先想清楚再做"

**不需要经过此 skill 的场景：**
- 用户需求已经非常清晰，可以直接进入 `make-dev-plan`
- 用户直接要求"帮我拆任务/做计划"，且信息完整
- 纯粹的 bug 修复、路径迁移、配置调整等目标明确的任务

## Checklist

按顺序完成以下步骤：

1. **探索项目上下文** — 检查相关文件、文档、最近提交
2. **逐个提问澄清** — 一次一个问题，理解目的、约束、成功标准
3. **提出 2-3 种方案** — 附带权衡分析与推荐
4. **呈现设计方案** — 按复杂度分节呈现，每节获得用户确认
5. **写设计文档** — 保存到 `.agents/docs/YYYY-MM-DD-<topic>-design.md`
6. **Spec 自检** — 检查占位符、矛盾、歧义、范围
7. **用户审阅 spec** — 请用户确认设计文档后再进入实现规划
8. **转入实现规划** — 调用 `make-dev-plan` 生成开发计划

## Process Flow

```text
探索项目上下文
    ↓
逐个提问澄清
    ↓
提出 2-3 种方案
    ↓
呈现设计方案 ← 用户不认可则回退修改
    ↓
写设计文档
    ↓
Spec 自检
    ↓
用户审阅 spec ← 用户要求修改则回退重写
    ↓
调用 make-dev-plan
```

**终止状态是调用 `make-dev-plan`。** 设计完成后，不得调用其他实现 skill。唯一允许的下游 skill 是 `make-dev-plan`。

## The Process

### Understanding the idea

- 先检查当前项目状态（文件、文档、最近提交）
- 在提问前先评估范围：如果需求涉及多个独立子系统，立即指出，不要在需要拆分的项目上花时间细化细节
- 如果项目太大，帮助用户拆分为子项目：哪些是独立部分、如何关联、按什么顺序构建？每个子项目各自走一遍 brainstorming -> make-dev-plan -> 落地 的循环
- 对范围合适的项目，一次一个问题逐步细化
- 优先使用选择题，但开放性问题也可以
- 每条消息只问一个问题 — 如果一个话题需要更多探索，拆成多条消息
- 聚焦于理解：目的、约束、成功标准

### Exploring approaches

- 提出 2-3 种不同方案，附带权衡分析
- 以对话方式呈现选项，给出推荐与理由
- 先给出推荐方案并解释为什么

### Presenting the design

- 当你认为已经理解了要构建什么，开始呈现设计方案
- 按复杂度调整每个 section 的篇幅：简单的几句话，复杂的 200-300 字
- 每个 section 结束后询问是否正确
- 覆盖：架构、组件、数据流、错误处理、测试
- 准备好回退澄清

### Design for isolation and clarity

- 将系统拆分为更小的单元，每个单元有清晰目的、定义良好的接口，可独立理解和测试
- 对每个单元，你应该能回答：它做什么、怎么用、依赖什么？
- 能否在不读内部实现的情况下理解一个单元？能否在不破坏使用者的情况下修改内部实现？如果不行，边界需要调整
- 更小、边界清晰的单元也更容易处理 — 你能更好地推理自己能一次放入上下文的代码，当文件聚焦时编辑也更可靠。文件变大往往是职责过多的信号

### Working in existing codebases

- 在提出变更前先探索当前结构。遵循已有模式
- 当已有代码存在影响当前工作的问题时（例如文件过大、边界不清、职责纠缠），将有针对性的改进作为设计的一部分 — 就像一个好的开发者在自己工作的代码中做的那样
- 不要提出无关的重构。聚焦于服务当前目标

## After the Design

### Documentation

- 将确认后的设计文档保存到：
  - `.agents/docs/YYYY-MM-DD-<topic>-design.md`
- 使用清晰简洁的写法
- 将设计文档提交到 git

### Spec Self-Review

写完设计文档后，用 fresh eyes 审视：

1. **占位符扫描：** 有 "TBD"、"TODO"、未完成 section 或模糊需求吗？修复它们。
2. **内部一致性：** 各 section 之间有矛盾吗？架构与功能描述匹配吗？
3. **范围检查：** 聚焦到足以作为单个实现计划吗？还是需要拆分？
4. **歧义检查：** 有需求可以被两种不同方式解读吗？如果有，选一种并明确写出来。

发现问题就直接修复。不需要再次审阅。

### User Review Gate

spec 自检通过后，要求用户审阅设计文档：

> "设计文档已保存到 `.agents/docs/YYYY-MM-DD-<topic>-design.md`。请审阅，如需修改请告诉我，确认无误后我们进入开发计划阶段。"

等待用户回复。如果用户要求修改，修改后重新执行 spec 自检循环。只有用户确认后才继续。

### Transition to implementation

- 调用 `make-dev-plan` 生成开发计划
- 不得调用其他任何 skill。`make-dev-plan` 是设计完成后的唯一出口

## Key Principles

- **一次一个问题** — 不要一次问太多
- **优先选择题** — 比开放性问题更容易回答
- **YAGNI** — 从所有设计中移除不必要的功能
- **探索替代方案** — 在确定前始终提出 2-3 种方案
- **增量确认** — 呈现设计，获得确认后再继续
- **灵活回退** — 当发现不合理时，回退澄清

## Anti-patterns

| 错误 | 正确 | 原因 |
|------|------|------|
| 所有需求都强制走 brainstorming | 只在需求不清晰时触发 | 避免过度设计、浪费时间 |
| 一次问多个问题 | 一次一个问题 | 用户容易遗漏或回答不全 |
| 跳过方案对比直接设计 | 先提 2-3 种方案再收敛 | 避免过早锁定单一方案 |
| 设计文档保存到错误路径 | 保存到 `.agents/docs/` | 与项目文档组织规范一致 |
| 设计完成后调用其他 skill | 唯一出口是 `make-dev-plan` | 保持三段式链路一致 |
