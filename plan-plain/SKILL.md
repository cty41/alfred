# plan-plain — 生成可执行计划，并强制人话化

计划要**能执行**，也要**能被人一眼看懂**。本 skill 在计划节点收束需求、写出可验收任务、落到计划文件，并在文件顶部固定写入「人话版」。

## Quick Reference

| 阶段 | 做什么 | 出口 |
|------|--------|------|
| 0 检测 | 是否已是计划节点（生成/整理/落盘/解释计划） | 是则继续；否退出 |
| 1 澄清 | P0 范围 → P1 方法 → P2 核心 → P3 权限（5–12 题） | 范围与边界收束 |
| 2 计划 | Background / Scope / File Structure / Tasks | 可验收、无占位符 |
| 3 落盘 | decision-complete 才写入 plans 目录 | 路径告知用户 |
| 4 人话版 | 强制写入 `## 人话版`（五段固定顺序） | 计划文件顶部 |

**人话版五段顺序（不可省略、不可乱序）**：一句话 → 为什么 → 步骤白话 → 怎样算完成 → 易踩坑。

**受众**：需要审阅或执行该计划的**开发者/人类**。目标是消掉 LLM 计划腔，不是幼稚化。

## When to use

- Agent 生成、拆分、修订或保存开发/实施计划时（自动视为计划节点）。
- 计划将写入 `.agents/plans/` 或项目约定的 plans 目录时。
- 用户点名 `plan-plain` / `/plan-plain`，或要求「人话版 / 大白话 / 把计划讲清楚 / 这计划看不懂」。
- 旧入口 `make-dev-plan`、`plan-mode-plan-writer` 被调用时（二者已指向本 skill）。

**不要**仅因回答可以更简单就触发；那是 `eli5`。**不要**解释与计划无关的任意技术主题。

## Workflow

### Step 0: 检测计划节点

满足任一即为计划节点：

1. 用户要求开发计划、任务拆分、里程碑、迁移/改造方案；
2. 即将写出含多个可执行任务与验收标准的文档；
3. 正在把已收束方案保存为正式计划；
4. 用户要求把现有计划讲成人话。

计划节点进入 Step 1；仅要求「给现有计划加人话版」可跳到 Step 4（仍须核对计划正文，不得虚构）。

### Step 1: 澄清（信息不足时）

规划前**必须先澄清**，除非用户信息已极其完整。按优先级提问，总题数 **5–12**，每组 2–3 个高价值问题即可；该组已足够可跳过后续组。

| 优先级 | 轴 | 问什么 |
|--------|----|--------|
| P0 | 改动范围 | 目标、边界、成功标准；In/Out；最不想动的模块 |
| P1 | 方法与工具 | 架构/模式、语言框架、工具链约束 |
| P2 | 核心设计 | 关键抽象、数据流、职责划分、为何这么拆 |
| P3 | 是否允许修改 | 逐项 yes/no；未答不得默认可改 |

**P3 未明确许可前，不得默认纳入**：共享基础库/公共 API、工具链与工程化、项目结构与边界。若计划仍依赖此类改动，写入 Assumptions，并在 Risks 标为待确认（尽量附不改基础的降级路径）。

用户未答的点：可做合理假设，但必须在计划中单独列出 **Assumptions**，不得隐含。

### Step 2: 写出可执行计划骨架

正文至少包含（聊天内计划可无 Summary；落盘计划在 Step 3 补 Summary）：

```markdown
## Summary
- 目标、成功标准、当前结论（落盘时必填）

## Background
- 当前问题：
- 目标：
- 预期收益：

## Scope
### In Scope
- 可交付且可验证的能力
### Out of Scope
- 明确不做的内容

## File Structure
- `路径/文件` — 单一清晰职责

## Tasks
### Task N: <名称>
- 目标：
- 输入：
- 输出：
- 涉及文件：
- 验收标准：
  - 可观察行为或检查命令
```

**任务拆分纪律**：

1. **MVP-first**：每个 Task 可独立完成、可验证。
2. **垂直切片**：按用户价值/可观察结果切，不按「先 data 再 view」技术分层切。
3. **命名一致**：类型、方法、路径跨 Task 呼应；禁止 Task 3 叫 `clearLayers()`、Task 7 叫 `clearFullLayers()`。
4. **禁止占位符**：TBD、TODO、「完成实现」、「添加适当错误处理」、「类似 Task N」— 全部算计划失败。

信息较多时可加 Phases、Risks & Open Questions。

### Step 3: 落盘（仅 decision-complete）

同时满足才写入文件：

- 目标与成功标准明确；
- 范围与「不做什么」已写清；
- 高影响选择已决定；
- 任务能按验收标准逐项完成。

否则只留在对话中继续收束，**不要**写入 plans。

**落盘要求**：

- 路径：项目约定 plans 目录（默认 `.agents/plans/`；项目说明覆盖则从其约定）。
- 文件名：清晰主题名，必要时带日期。
- 执行上下文补全：Summary、Current State、Relevant Context、Implementation、Test Plan、Risks/Assumptions、Handoff Notes（先读什么、先验证什么、不要做什么）。
- 回复用户完整路径与关键范围。
- 收尾约定：实现验证后，把长期结论迁入权威文档、更新知识索引、删除已完成计划（由版本历史保存）。

### Step 4: 强制写入「人话版」

**无论计划只在聊天还是写入文件，都要人话化。** 写入文件时，节标题固定：

```markdown
## 人话版

### 一句话
…

### 为什么
…

### 步骤白话
…

### 怎样算完成
…

### 易踩坑
…
```

**位置**：`Summary` 之后（聊天内无 Summary 则在标题后、实现细节之前）。全文档只出现一处。

**各段合同**：

| 段 | 要求 |
|----|------|
| 一句话 | 计划要改变什么；≤40 字优先 |
| 为什么 | 不做会怎样 / 解决的真实痛点；≤2 句 |
| 步骤白话 | 把 Tasks 译成「先…再…；做完能看到…」；禁止复读任务标题 |
| 怎样算完成 | 可观察结果；对照验收但用短句 |
| 易踩坑 | 1–3 条最易误解的边界/假设/术语；没有则写「暂无」 |

**语言规则**（开发者受众）：

- 短句；先结论后细节。
- 不出现未解释的内部缩写；必要术语括号内一句定义。
- 类比可以有，但必须紧挨字面含义；禁止只有类比没有机制。
- 不夸大、不隐藏重要限制。
- **与正文事实一致**：不引入计划里没有的承诺，不删掉已写明的禁止项。
- 长度一屏优先（约 15–35 行）；任务多时步骤白话可按阶段合并，但每步都要有「完成时能看到什么」。

### Step 5: Self-Review（写完计划后）

1. 需求每项都能指向某个 Task？缺口补任务或写明 Out of Scope。
2. 占位符扫描：命中「禁止占位符」任一模式则改掉。
3. 一致性：跨 Task 命名/路径/接口一致。
4. 人话版五段齐全、顺序正确、与正文无事实冲突。

## Anti-patterns

| 错误 | 正确 | 原因 |
|------|------|------|
| 只交任务列表不写人话版 | 强制 `## 人话版` 五段 | 人看不懂的计划无法审阅 |
| 步骤白话复读任务标题 | 写成「做什么 + 做完能看到什么」 | 复读不降低理解成本 |
| 只有类比没有字面含义 | 类比与真实机制成对出现 | 类比会误导边界 |
| 未澄清就输出完整计划 | 先 P0→P3 收集关键信息 | 避免计划偏离真实目标 |
| 默认可改基础库/工具链/结构 | 未获许可写入 Assumptions/Risks | 避免越权规划 |
| 验收标准写「完成实现」 | 写可观察行为或检查命令 | 否则无法判断是否完成 |
| 验收含 TBD/TODO | 写具体可验证内容 | 占位符使计划不可执行 |
| 按技术分层拆 Task | 按垂直切片/用户价值拆 | 便于迭代和验收 |
| 草案写入 plans | 只保存 decision-complete | 减少死计划 |
| 人话版擅自加戏/删禁止项 | 与计划正文逐条对齐 | 解释不得改变承诺 |
| 解释任意技术话题 | 转 `eli5` 或普通回答 | 本 skill 只服务计划节点 |

## Checklist

- [ ] 已识别为计划节点（或用户显式调用）
- [ ] 澄清覆盖 P0–P3 中必要轴；未授权基础改动未默认纳入
- [ ] 计划含 Background / Scope / File Structure / Tasks
- [ ] Task 垂直切片、可独立、可验证、无占位符
- [ ] decision-complete 才落盘；路径已告知用户
- [ ] `## 人话版` 五段固定顺序且位置正确
- [ ] 语言为开发者可读短句；术语已解释；类比不空心
- [ ] 人话版与正文事实一致
- [ ] 已执行 Self-Review

## 协作关系

- 任意主题、任意受众的通俗解释 → `eli5`
- 旧计划入口 `make-dev-plan` / `plan-mode-plan-writer` → 已由本 skill 取代
- 文档位置与完成后清理 → 项目约定（如 `project-doc-organization`）
